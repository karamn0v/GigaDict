# Архитектура

Решение состоит из шести проектов:

- `GigaDict.Core` — настройки, снимок задачи, явная машина состояний, FIFO, лимиты RAM, история и логика границ текста.
- `GigaDict.Audio` — WASAPI shared mode через NAudio, RAM-буфер, downmix и WDL-ресемплинг в PCM16 mono 16000 Гц.
- `GigaDict.Recognition` — HTTP, WebSocket protocol 1.0 и ограниченные повторы.
- `GigaDict.Input` — `WH_KEYBOARD_LL`, WinEvent focus hook, UI Automation COM, `SendInput` и Clipboard.
- `GigaDict.App` — WinForms, `NotifyIcon`, настройки, single-instance, автозапуск и координация.
- `GigaDict.Tests` — платформонезависимые unit/transport tests.

## Потоки данных

Keyboard hook выполняет только обновление маленькой state machine и постановку события в ThreadPool. WASAPI callback копирует очередной блок в ограниченный RAM-буфер. После отпускания клавиши преобразование аудио выполняется вне callback, а неизменяемый снимок настроек и привязки фокуса попадает в FIFO.

Один worker последовательно вызывает выбранный транспорт. Отдельный channel вставки получает результаты, поэтому ожидание отпускания следующей горячей клавиши не занимает worker распознавания. Каждая задача сохраняет собственные настройки и собственный `FocusIdentity`.

## Безопасность вставки

В начале записи фиксируются HWND, PID и UI Automation Runtime ID. WinEvent `EVENT_OBJECT_FOCUS` действует на протяжении жизни задания: любое несовпадение необратимо запрещает автовставку. Перед вставкой идентичность проверяется снова, а при Unicode-вводе — между блоками символов. Неизвестные, password, disabled и не-Edit/Document элементы запрещены. Фокус никогда не восстанавливается программно.

Собственные события `SendInput` имеют `dwExtraInfo` marker и игнорируются hook. Повторная сетевая попытка помечает результат и запрещает запоздалую автовставку.

## Память и завершение

Аудио существует только как массивы в памяти. HTTP-запрос потоково добавляет WAV-заголовок без второго полного WAV-буфера; WebSocket передаёт PCM блоками. После распознавания/ошибки/отмены массив очищается. Настройки сохраняются через временный файл и атомарное переименование; распознанный текст в них не попадает.
